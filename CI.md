# Проверки на GitHub (CI)

Тесты гоняет GitHub Actions: настройки лежат в `.github/workflows/`. Ваш компьютер для этого не нужен.

## Что запускается

| Когда | Файл | Что делает | Сколько идёт |
|---|---|---|---|
| Каждый push в любую ветку и каждый pull request | `ci.yml` | `node --check` всех js-файлов; `tests/run.js --quick`, разбитый на 4 параллельные части; игра в Chrome (профиль desktop, быстрый режим); итоговая строка **ok** | 5–10 мин |
| Каждую ночь в 04:00 МСК (и по кнопке) | `nightly.yml` | полный `tests/run.js` (по воскресеньям `--long`); soak: 1 игровой час на сиде 1; deficit: 8 игровых суток на сиде 1 | до 1 ч |

**Сайт они не трогают.** GitHub Pages публикует сайт прямо из ветки `main` (Settings → Pages → «Deploy from a branch»), отдельно от этих проверок. Красная проверка не остановит публикацию: остановит её только защита ветки (ниже), потому что тогда красный код просто не попадёт в `main`.

## Ложные красные

Часть тестов (house, unions, kids, tempo) иногда падает просто потому, что машина загружена. Поэтому в CI упавшая проверка **повторяется один раз** (`--retry 1`):
- прошла со второй попытки — она жёлтая, с замечанием «нестабильна: прошла с 2-й попытки…», а прогон зелёный;
- упала оба раза — прогон красный, это похоже на настоящую ошибку.

Если весь прогон всё равно покраснел из-за нагрузки, откройте прогон и нажмите **Re-run failed jobs**: перезапустятся только упавшие части.

Локально то же самое: `npm run test:ci` (быстро, с повтором) или `node tests/run.js --retry 1` (полностью).
Новые ключи `tests/run.js`: `--quick` (один сид, симуляция покороче), `--shard 2/4` (только вторая четверть проверок), `--retry N`.

## Где смотреть результат

1. GitHub → вкладка **Actions** → нужный прогон.
2. Внизу страницы прогона есть **сводка** (Summary): таблица проблем, по строке на проверку.
3. В разделе **Artifacts** лежат полные логи и JSON-отчёты: `tests-1…4`, `browser` (скриншоты), `nightly-full`, `nightly-soak`, `nightly-deficit`. Хранятся 14 дней для push и 30 дней для ночных.
4. Ночной прогон по кнопке: Actions → **nightly** → **Run workflow** (галочка «long» включает длинный прогон).

## Как включить защиту ветки main (делаете вы сами, 2 минуты)

После этого в `main` нельзя будет влить код, пока проверка **ci / ok** не станет зелёной.

1. Откройте https://github.com/xXxLexolasxXx/OldGold/settings/rules (Settings → **Rules** → **Rulesets**).
2. **New ruleset** → **New branch ruleset**.
3. **Ruleset name**: `main`. **Enforcement status**: **Active**.
4. **Target branches** → **Add target** → **Include default branch**.
5. Включите галочки:
   - **Restrict deletions** (ветку `main` нельзя удалить);
   - **Block force pushes**;
   - **Require status checks to pass** → **Add checks**, впишите `ok` и выберите **ok** (источник GitHub Actions).
     Можно также включить «Require branches to be up to date before merging», но тогда перед каждым слиянием придётся подтягивать свежий main. Для начала лучше оставить выключенным.
6. **Не** включайте «Require a pull request before merging», если сессии Claude должны и дальше пушить в `main` напрямую. Учтите: с одной только проверкой статуса прямой push в `main` тоже отклоняется, ведь у нового коммита ещё нет зелёной галочки. Есть два рабочих варианта:
   - **Строго (рекомендую):** весь код идёт через ветки и pull request; кнопка Merge станет доступна только после зелёного **ok**. Сайт обновляется после слияния.
   - **Мягко:** в **Bypass list** добавьте себя (Add bypass → Repository admin). Тогда вы и сессии от вашего имени можете пушить в `main` напрямую, а проверка будет обязательной для всех остальных и для pull request.
7. **Create**.

Чтобы выключить защиту: та же страница → ruleset `main` → **Enforcement status: Disabled**.

Если в списке **Add checks** нет `ok`, дождитесь хотя бы одного прогона `ci` (GitHub предлагает только проверки, которые уже запускались).
